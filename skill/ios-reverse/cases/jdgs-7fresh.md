# 案例：七鲜 jdgs 加密头（进行中）

**状态：未解出纯算法。** 这份文档记录已确认的事实与否证，避免接手的人重走。

## 目标

七鲜（`com.xstore.sevenFresh`，RN/Hermes，主二进制 106MB）的 `jdgs` 请求头：

```json
{"b1":"<appkey UUID>","b2":"3.0.55_1","b3":"3.0","b4":"<base64 716/720 字符>",
 "b5":"<64 hex>","b6":"<64 hex>","b7":"<ms 时间戳>"}
```

## 已确认（可复现）

### 入口

```
+[JDGB_unquilleted maHWP__unpliableness:errCode:]
```

`objc_call` 当 oracle 调用，`args[0]` 是 `"POST /api <bodySha>=&functionId=<fid>"`。
返回完整 jdgs JSON 字符串。`errCode` 用 `{"$intptr":0}` 传地址，回读在 `out_params`。

### 字段性质

| 字段 | 性质 | 证据 |
|---|---|---|
| b1 | appkey UUID，明文 | 直接读 |
| b2 | `3.0.55_1`，明文 | 直接读 |
| b3 | `3.0`，明文 | 直接读 |
| b4 | 需要解的那块 | 长度在 535/536/537 之间变 |
| b5 | 纯函数 | 同输入 5 次完全相同 |
| b6 | 每次不同，**且跨进程也不同** | 单进程内看似稳定，换进程全变 |
| b7 | 毫秒时间戳 | 直接读 |

### b4 的长度约束（强判据）

原始字节长度在 **535 / 536 / 537** 之间变化：

- `len % 16 != 0` → **排除带 padding 的 AES-CBC/ECB**
- `len % 4 != 0` → **排除 XXTEA**
- 长度会变 1 字节 → 不是固定长度的分组结构

这一条能省掉大量无用功，先算再猜。

### b4 是自引用但收敛

抓 `0x100200c4c`（字段追加器）的 `x1`，能看到**内层 jdgs JSON**：

```json
{"b1":"...","b2":"3.0.55_1","b3":"3.0","b4":"<同一个 b4>","b5":"<同一个 b5>","b7":"<同一个 b7>"}
```

注意：**内层没有 b6**，且内层 `b4` 与外层**逐字节相同**。

这排除了「b4 = 加密(包含 b4 自己的 JSON)」——那会无限增长。
正确理解：**b4 的明文不含 b4 自己**，内层 JSON 只是同一个结构体的另一次渲染。

`0x104102d10` 的 descriptor 字符串表顺序是 `b1 b2 b3 b4 b5 b7 b6`，
b6 排在最后，与「b6 是最后才加上的」一致。

### 字段构建链路

```
maHWP(0x1001eb7a0)
  → core(0x100186468)        入口桩，保存入参后尾调用
  → 0x100186744              字段构建器
       ├─ 0x100200f54  建 builder (w0=8, w1=0x138, w2=0x106e,
       │                             x3=0x104101720, w4=0x36, x5=0x104102d10)
       ├─ 0x100200c4c × 6   追加字段 —— **这是栈式写入器**，不是 append
       ├─ 0x100200c0c × 1   追加 int64（b7）
       └─ 0x1001f5b40       编码
```

`0x100200c4c` 的真实形态（反汇编）：

```asm
ldr x9, [x0, #0x30]     ; 栈顶指针
sub x9, x9, #8          ; 向下增长
ldr x10, [x0, #0x18]    ; 下界
cmp x9, x10
b.hs ok
mov w0, #0xb            ; 0xb = 溢出错误码
ok:
str x9, [x0, #0x30]     ; 更新栈顶
str x1, [x9]            ; 写入值
```

**逆序压栈**，所以 descriptor 里字段名是倒着的。这排除了「按顺序 append 的 protobuf builder」。

## 已否证（不要重试）

- **`0x1001f5b40` 不是序列化器**，是 protobuf **解码器**（`0x104109ca0` 跳转表 + `br x8` 分派，
  逐字节消费 `ldrh w8,[x22]; eor w8,w8,w23; cmp w8,#0x23a`）。
  所以 `0x104d322f0` 是 **vtable（8 个代码指针）**，不是 key。
- b5/b6 ≠ 任何 1/2/3 字段的 MD5/SHA1/SHA256/SHA512（含 `[:64]`/`[64:]` 切片），
  ≠ HMAC 全族（key 试过 appkey/eid/umid/lid/b1/b2/b3/b7/CCCrypt key）。
- b4 ≠ zlib / raw-deflate / gzip（全部解不开）。
- b4 ≠ 标准 FlatBuffers（前 4 字节 uoffset 越界到 4GB）。
- b4 ≠ 标准 protobuf（首字节不是合法 tag）。
- b4 与「不含 b4 的 JSON」长度差不是固定值（165→372、237→300），所以不是「JSON + 固定头」。
- b4 与 JSON 的 XOR 没有周期（周期 64 的 64/536 匹配是恒等式巧合）。

## 还没做

1. **`0x100200f54` 返回的对象结构**——那才是真正的 encoder，b4 的明文缓冲应该在它内部。
   下一步应该 `objc_dump_ivars` 或直接读它的字段。
2. b6 的进程级种子来源（跨进程全变，说明有进程级随机量参与）。
3. b5 与 b4 的关系（是否 `sha256(b4raw)` 的某种变体——已排除直接 sha256）。

## 工具侧已经为这个案例加的能力

- `capture_multi`：一次 hook 抓多个寄存器（换寄存器要重启进程，这是刚需）
- `capture_ret_multi`：抓返回值寄存器指向的缓冲（`(status, buffer)` ABI，缓冲返回后即释放）
- `objc_call` 的 `{"$intptr":N}`：传 int 出参地址并回读
- `capture_after`：出参缓冲在返回后才写好的情况

## 教训

- 我用「AES 解密后没有可打印明文」排除 AES，但**明文是二进制结构**，这条判据不成立。
  排除一个算法前先问：假设它确实是那个算法，这个判据还成立吗？
- 我误判过一次「二进制会自解密改写代码段」，真相是进程重启后 slide 变了、我用了旧 slide。
- `return_address` 过滤对 inline hook 不生效，别指望用它分离同函数的不同调用点。
